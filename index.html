Real-Time E-Commerce Streaming Pipeline

Cloud Data Engineering Project

  • Python
  • Azure Event Hubs
  • Azure Stream Analytics
  • Azure Cosmos DB
  • Azure SQL Database
  • Power BI

Problem

E-commerce teams typically see customer behaviour (cart abandonment, unusual spikes, drop-offs) hours later in a batch report, by which point the moment to act on it has passed.

Architecture

  1. Simulated event source – Python producers, 400+ events/sec
  2. Azure Event Hubs – ingestion layer
  3. Azure Stream Analytics – windowed queries, anomaly detection
  4. Cosmos DB + Azure SQL – dual-write for flexible + relational access
  5. Power BI – DirectQuery live dashboard, AI Key Influencers

Key Metrics

  • 400+ events/sec ingested
  • 2 databases written concurrently
  • Dead-letter routing, dedup, and late-arrival handling built in

Trade-offs

Why two databases? Cosmos DB handles fast, flexible writes for downstream flexibility; Azure SQL Database keeps a structured, relational copy for BI tooling that expects tabular data. Splitting the write path avoided forcing one database to do both jobs well.

Why build in fault tolerance? Dead-letter routing catches events that fail processing so they don't silently disappear, duplicate detection prevents double-counting, and late-arrival handling accounts for out-of-order events, standard concerns in production streaming that are easy to skip in a student project.

NWU Classroom Polling Platform

Full-Stack Real-Time Engagement Platform

  • React 19
  • Node.js
  • TypeScript
  • PostgreSQL
  • Redis
  • Socket.io
  • Docker
  • Nginx

Problem

Large lecture classes give lecturers little live signal on whether students are following along, and students are often reluctant to speak up or be identified when confused.

Architecture

  1. React 19 + TypeScript client – student, lecturer, admin views
  2. Socket.IO – real-time question/response delivery
  3. Node.js API – JWT auth, bcrypt password hashing
  4. PostgreSQL + Redis – persistent data + session/cache layer
  5. Nginx + Docker – reverse proxy, containerised deployment

Key Metrics

  • ~15,000 lines of code
  • 14-week development cycle
  • Sub-millisecond live response synchronisation

Trade-offs

Why Socket.IO instead of polling the API? Live results need to feel instant – Socket.IO gives sub-millisecond delivery rather than students refreshing or the client polling on an interval.

How is multi-role access secured? JWT authentication with bcrypt-hashed passwords separates Student, Lecturer, and Admin roles, while Redis-backed caching keeps session lookups fast under concurrent load without hitting PostgreSQL on every request. The platform also supports POPIA-compliant anonymous guest access, so students can participate without their identity being tied to a response.
